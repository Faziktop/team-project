# АИС «QuestEvent» — автоматизированная система управления квест-ивентами

Веб-приложение на **Python 3.12 / Flask 3.x / SQLite** для локального
развёртывания, реализованное по техническому заданию
(см. `Техническое_задание.docx`), с модульной архитектурой (Application
Factory + Blueprints + слоистая архитектура Presentation → Service →
Repository/ORM → Domain).

## Возможности

Реализованы все подсистемы из ТЗ (п. 4.1.1, п. 4.2):

1. **Бронирование и расписание** — календарь загрузки по комнатам, генерация
   сеансов, защита от двойного бронирования (на уровне бизнес-логики и БД),
   гибкие тарифы по дню недели/времени/числу игроков, промокоды и сертификаты
   (учитываются в стоимости; бронь подтверждается сразу при создании — без
   отдельного шага оплаты).
2. **Управление квестами, локациями и ресурсами** — филиалы → локации →
   комнаты → квесты; вывод комнаты на обслуживание; чек-листы подготовки
   комнаты к сеансу.
3. **CRM** — карточка клиента с историей бронирований и отзывов, программа
   лояльности (баллы/статус), поиск по базе клиентов.
4. **Ценообразование** — сертификаты и промокоды учитываются при расчёте
   стоимости брони; отдельный модуль оплаты/эквайринга в системе отсутствует —
   бронирование подтверждается сразу при создании.
5. **Уведомления** — подтверждение брони, напоминания за 24ч/2ч, запрос
   отзыва после игры, уведомления администраторам (пишутся в лог приложения
   и в таблицу `Notification` — см. «Известные ограничения» ниже).
6. **Администрирование и RBAC** — роли: суперадминистратор, администратор
   локации, ведущий квеста, менеджер, бухгалтер, клиент; multi-tenant по
   филиалам; журнал аудита критичных операций.
7. **Отчётность и аналитика** — загрузка комнат, выручка/конверсия/средний
   чек, эффективность квестов и сотрудников, экспорт в CSV/Excel, дашборд KPI.
8. **Публичный веб-виджет** — выбор квеста → дата/время (AJAX) → бронирование
   в 3 шага → мгновенное подтверждение; личный кабинет клиента; гостевой
   поиск брони по коду+телефону.

## Архитектура и структура проекта

```
app/
  __init__.py            # Application Factory
  config.py               # Конфигурации (development/testing/production)
  extensions.py            # db, migrate, login_manager, csrf, cache
  constants.py              # Роли, статусы, перечисления (единый источник правды)
  models/                    # SQLAlchemy ORM (Domain + Data Access)
  services/                   # Бизнес-логика (не зависит от Flask/HTTP)
    pricing_service.py          # расчёт тарифов и скидок
    schedule_service.py          # генерация и выдача слотов расписания
    booking_service.py            # оркестрация бронирования/отмены (защита от гонок)
    notification_service.py         # уведомления (локально, лог + таблица Notification)
    report_service.py                # отчёты и экспорт CSV/XLSX
    audit_service.py                  # журнал аудита
  forms/                       # WTForms (валидация)
  blueprints/                   # Presentation-слой (Flask Blueprints)
    auth/ admin/ schedule/ crm/ payments/ reports/ widget/
  tasks/                          # APScheduler: напоминания клиентам/отметка завершения броней
  templates/, static/               # Jinja2 + Bootstrap 5
migrations/                          # Alembic (Flask-Migrate)
tests/                                 # pytest — бизнес-логика, RBAC, e2e-сценарии
seed.py                                  # демо-данные
```

Ключевые технические решения (согласно ТЗ п. 4.2.4):

- **Защита от двойного бронирования**: два независимых рубежа — проверка
  `Slot.status == available` перед созданием брони и частичный уникальный
  индекс `(slot_id) WHERE status != 'canceled'` на уровне БД, перехватывающий
  гонку параллельных запросов (`IntegrityError → SlotConflictError`).
- **Версионирование тарифов**: тарифы не удаляются физически, чтобы не терять
  расчёты по завершённым бронированиям.
- **RBAC**: единая таблица `users` с полем `role` и декораторами
  `@roles_required(...)` / `@staff_required`; данные фильтруются по филиалу
  через `branch_scoped_query`.
- **Уведомления работают полностью локально** (без обращения к внешним
  серверам) — см. «Известные ограничения» ниже. Модуль оплаты в системе
  отсутствует: бронь подтверждается сразу при создании.
- **Целостность данных SQLite**: `PRAGMA foreign_keys=ON` и `journal_mode=WAL`
  включаются на событии `connect` (`app/extensions.py`) для каждого соединения —
  без этого SQLite не проверяет внешние ключи на уровне БД.
- **Журнал аудита**: запись в `AuditLog` фиксируется в той же транзакции,
  что и основная операция (коммит один — после `log_action()`), поэтому
  событие не теряется при завершении запроса; для не-суперадминов
  `/admin/audit-log` ограничен действиями сотрудников их собственного филиала.

## Быстрый старт

```bash
python3.12 -m venv venv
source venv/bin/activate            # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env                 # ОБЯЗАТЕЛЬНО задайте SECRET_KEY (команда для генерации — в .env.example)

export FLASK_APP=run.py              # Windows (PowerShell): $env:FLASK_APP="run.py"
flask db upgrade                      # применяет миграции Alembic
flask seed-demo                        # наполняет БД демо-данными

python run.py                           # http://127.0.0.1:5000
```

По умолчанию сервер слушает **только localhost** (`HOST=127.0.0.1`). Чтобы открыть его в сети,
задайте `HOST=0.0.0.0` — при этом режим отладки Werkzeug принудительно отключается (интерактивный
отладчик нельзя выставлять в сеть). Для продуктивного запуска используйте `FLASK_CONFIG=production`,
WSGI-сервер (gunicorn/waitress) и reverse-proxy с HTTPS.

Приложение полностью самодостаточно и работает локально на одном компьютере
(Flask + SQLite-файл в `instance/questevent.db`), без Docker и без внешних
сервисов.

## Безопасность

Подробный разбор находок и исправлений — в `SECURITY_REVIEW.txt` (два раунда). Кратко:

- **Аутентификация:** временная блокировка учётной записи после 5 неудачных входов (15 мин), одинаковое время
  и текст ответа для существующего и несуществующего email, новая сессия после входа (защита от session
  fixation), срок сессии 8 ч, `session_protection="strong"`, политика паролей (≥ 8 символов, буква + цифра,
  не из списка типовых, не совпадает с логином, ≤ 128 символов).
- **Сессии/CSRF:** выход только через POST с CSRF-токеном; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в production.
- **Content-Security-Policy:** `script-src 'self'` — в шаблонах нет inline-JS (тест это проверяет). Bootstrap,
  иконки и шрифты лежат в `app/static/vendor/`, внешних CDN нет — приложение работает без интернета.
  Также: `X-Frame-Options`, `Permissions-Policy`, `Cross-Origin-*`, HSTS, `Cache-Control: no-store` для страниц с ПДн.
- **Доступ (RBAC):** fail-closed — сотрудник без филиала и аноним не получают данных; администратор локации
  управляет только линейным персоналом своего филиала; последнего активного суперадмина нельзя заблокировать.
- **Целостность денег:** лимит промокода и баланс сертификата списываются атомарными `UPDATE … WHERE`, возврат на
  сертификат ограничен номиналом; отмена возвращает использование промокода.
- **Ввод:** типизированные `DateField/TimeField`, строгие форматы телефона/кода/времени, лимиты диапазонов
  (расписание ≤ 93 дн., отчёт ≤ 366 дн., публичный API ≤ 31 дн.), экранирование `LIKE`, защита от formula
  injection в CSV/XLSX, санитизация значений в логах.
- **Развёртывание:** `SECRET_KEY` проверяется на длину и «заглушечные» значения; `ProxyFix` включается только явно
  (`PROXY_FIX_HOPS`); `run.py` слушает localhost и не запускает отладчик в сети; планировщик не дублируется
  под reloader'ом.

## Известные ограничения демо-версии

По вашей просьбе система рассчитана исключительно на **локальное
развёртывание**, без Docker и без модулей подключения к внешним серверам.
Это отражается на двух пунктах ТЗ, которые в оригинале предполагают
интеграцию с платными внешними сервисами:

- **Оплата** — модуль оплаты/эквайринга в системе не реализован: бронь
  подтверждается сразу при создании, без отдельного шага оплаты. Расчёт
  стоимости с учётом тарифов, промокодов и сертификатов сохранён.
- **Уведомления** (`app/services/notification_service.py`) — вместо
  реальной отправки email/SMS уведомление записывается в лог приложения
  (`logs/questevent.log`) и в таблицу `Notification` в базе данных — там
  видно, кому и что должно было прийти. Вся логика «когда отправлять»
  (подтверждение, напоминания за 24ч/2ч, запрос отзыва) работает и покрыта
  тестами.
- **PDF-экспорт отчётов** не реализован (только CSV/Excel).
- **Гостевая бронь без подтверждения телефона.** Клиента без пароля находят по номеру телефона, поэтому
  человек, знающий чужой номер, может оформить бронь «на него» (она появится в его кабинете). Для реального
  запуска нужен SMS-код подтверждения; в локальной версии, где SMS не отправляются, он не реализован.
- **Rate limiting и кеш хранятся в памяти процесса** (`memory://`, `SimpleCache`): работают корректно при одном
  процессе; для нескольких воркеров задайте `RATELIMIT_STORAGE_URI=redis://…`.
- **Время сеансов хранится «наивным» местным временем площадки** (так его вводит администратор), а служебные
  метки (`created_at` и т. п.) — в UTC. Сервер должен работать в часовом поясе площадки.
- Частичный уникальный индекс брони (`sqlite_where`) специфичен для SQLite; при переезде на PostgreSQL его
  нужно описать через `postgresql_where`.
- Автоначисление баллов лояльности не реализовано (поля и статусы редактируются вручную в CRM).
- Двухфакторная аутентификация (2FA) — поле `two_factor_enabled`
  предусмотрено в модели `User`, сам механизм не реализован.
- Нагрузочные показатели раздела 4.1.3 (200+ одновременных пользователей)
  не проверялись — для локального запуска это не требуется; SQLite подходит
  для однопользовательской/небольшой командной эксплуатации.
